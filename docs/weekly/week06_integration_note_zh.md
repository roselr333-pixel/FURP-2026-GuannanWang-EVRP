## 2. Method Design（方法设计）

### 2.1 统一工作流

整条 pipeline 是：

```
instance（随机生成） → 卡车 EV 路线（V1） → 无人机任务分配（V2） → 评估（makespan / 可行性 / 违约）
```

三个变体只在"打开哪些约束"上不同，构造核心完全一致：

| 变体 | 建模内容 | 角色 |
|---|---|---|
| V0 | 纯卡车，无电池限制 | 参考下界 |
| V1 | 纯卡车 EVRP-TW（电量 + 充电 + 时间窗） | 基线 |
| V2 | 地面-空中协同 EVRP-TW（V1 + 无人机协同） | 我的改进 |

这样 V1 与 V2 之间的差距，纯粹是"加了无人机协同"带来的，两者求解器质量相同，对比因此是公平的。

### 2.2 卡车 EV 路线（V1 核心）

- 用最近邻排序 + 贪心顺序服务客户。
- 沿路线耗电（每单位距离耗 `RHO = 1.0` 电量），电量不足时在最近充电站充满（充满固定耗时 `RECHARGE = 40`，即"换电池"假设）。
- 每个客户有 `[e, l]` 时间窗：到达早于 `e` 则等待，晚于 `l` 记为时间窗违约。

### 2.3 无人机任务分配（V2 改进）

无人机由卡车携带，在卡车节点 *i* 起飞、在之后的某节点 *j* 回收，途中可顺序服务若干客户。一次无人机飞行必须满足三条约束：

1. **航程**：飞行总长 `i →（途经客户）→ j` 不超过无人机航程 `R_D = 160`；
2. **同步**：无人机在 *j* 落地的时间不晚于卡车到达 *j*（无人机可以等，但不能在卡车离开后才落地）；
3. **时间窗**：被服务的客户满足各自的时间窗。回收时无人机电量重置。

**相对上一版的改进**：上一版每次只卸 1 个客户，协同收益很小；这一版允许一次飞行服务最多 2 个客户，并且同一个卡车停靠点可以被无人机多次起降利用。

**启发式流程**：以 V1 卡车路线为基准，反复扫描路线上所有"起飞段 (i, j)"，对每段枚举可服务的客户组合（单客户 + 双客户两种方案），只要"把这组客户从卡车路线移除能降低卡车 makespan"就接受，直到再也找不到可接受的方案。这样既让无人机尽量多卸，又保证每一次卸都确实对完工时间有帮助。

### 2.4 目标

最小化完工时间 makespan = max(卡车完成时间, 无人机完成时间)。

## 3. Experiment Plan（实验计划）

- **算例**：随机生成，4 种规模 N = {8, 12, 16, 20} 个客户，各配 4 个充电站；客户与充电站位置、时间窗、需求均由固定随机种子决定，可复现。
- **种子**：每种规模跑 10 个随机种子（种子基 `20260720`）= **40 个算例**，满足 lab "≥10 算例 + 3 种规模 + 多种子" 的硬要求。
- **参数**：卡车速度 `V_T = 1.0`、无人机速度 `V_D = 2.0`、无人机航程 `R_D = 160`、电池容量 `Q = 250`、充电时间 `RECHARGE = 40`、服务时间 `SERVICE = 10`、能耗系数 `RHO = 1.0`。
- **报告指标**（对齐项目页最低标准）：目标值（makespan + 总距离）、可行性、时间窗违约、电量/能量违约、充电次数与充电时间、同步违约（被单机物理调度拒绝的飞行次数）、卸载客户数、运行时间、随机种子与参数。
- **失败案例**：额外构造 4 个针对性算例（FC1–FC4）做约束级诊断，见 §4.3。

## 4. Preliminary Result（初步结果）

### 4.1 主要对比（40 算例均值）

> 2026-09-13 主评估器物理化后按新口径重跑，本节数值已同步更新（见 `docs/analysis/evaluator_physical_fix_note_zh.md`）。

| 规模 | V0（参考下界） | V1（基线） | V2（改进） | V2 vs V1 | 平均卸载 | 卸载率 | V2 可行性 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 8 | 434.7 | 485.8 | 324.2 | **−33.6%** | 2.5 / 8 | 31.2% | 100% |
| 12 | 614.4 | 694.7 | 525.4 | **−24.5%** | 2.6 / 12 | 21.7% | 100% |
| 16 | 816.6 | 975.9 | 783.9 | **−19.6%** | 2.9 / 16 | 18.1% | 100% |
| 20 | 1080.1 | 1283.6 | 1078.4 | **−15.6%** | 2.9 / 20 | 14.5% | 100% |

- 40 个算例全部可行（V0 / V1 / V2 可行性均 100%，且每个 V2 计划都通过物理评估器）。
- V2 相对 V1 的平均改善在 **16%–34%** 之间（N=20 → N=8），逐种子波动为 7.3%–48.9%，说明协同收益是稳定的，不是某一次特例种子造成的。
- 平均卸载率 14%–31%（每算例 2–3 个客户）：只有一架无人机时同一时刻只有一个架次在飞。

### 4.2 怎么读这个结果

改善来自用更快的无人机替卡车跑掉一部分远端客户，而不是少充了电——V1 与 V2 的充电次数几乎相同。V0（无电池限制）的 makespan 比 V1 略低，说明电池 / 充电约束确实给卡车路线带来了额外代价，而 V2 通过无人机绕开了其中一部分。这一点恰好印证了"地面-空中协同"这条主线值得继续做下去。

### 4.3 失败案例（约束级诊断）

| 编号 | 设置 | 出了什么问题 | 说明 |
|---|---|---|---|
| FC1 | 纯电动卡车，关闭充电，电池 = 120 | 电量违约（一次充满也不足以覆盖） | 必须允许充电或加大电池 |
| FC2 | 协同，无人机航程 = 40（极小） | 仅卸 2 个客户，V2 ≈ V1 | 航程太小则无人机形同虚设 |
| FC3 | 纯电动卡车，时间窗很紧（宽度 = 35） | 10 个客户超窗 | 紧窗会直接击穿可行性 |
| FC4 | 协同，16 客户 | 7871 架次被单机物理调度拒绝 | 单机调度约束确实在起作用，且是瓶颈 |

FC4 特别值得记一笔：上一版因为每次只卸 1 个客户，同步约束几乎没被触发；这一版物理化后「架次不能重叠」让单机调度真正成了限制因素——这反过来说明，这次"改进"确实动到了问题的关键约束，而不是只在无关紧要的地方做文章。

### 4.4 关于学习方法扩展（Track C / D）的说明

本周 lab 也鼓励探索 RL / DL。我目前**没有**切换到 Track C / D，原因很实际：

- 我的算例仍很小（≤ 20 客户），而 RL / DL 通常需要大量样本与更真实的规模才能体现价值；在这么小的算例上，一个可解释的构造式启发式已经能给出清晰、稳定的对比。
- Track B 先把"问题变体 → 基线 → 改进 → 失败分析"这条研究工作流跑通，本身就是 lab 的核心目标；RL / DL 可以作为后续（W7 / W8）在已有基线上叠加的扩展，而不是现在另起炉灶。

这并不表示学习方法不重要，只是从"先搭一套可复现的工作流"这个角度，当前阶段把 Track B 做扎实更合适。

## 5. 局限

- **仍是贪心，不是优化。** 路线是最近邻 + 贪心插入，没有局部搜索，绝对数值离最优很远。重点在于变体之间的对比是公平的，不在于绝对值。
- **每架飞行最多 2 个客户。** 枚举限制在单 / 双客户以控制运行时间（双客户已是 O(n⁴) 枚举）。
- **还没复现论文。** 这是我自己的启发式，尚未把 Schneider (2014, E-VRPTW) 或 Murray & Chu (2015, FSTSP) 作为已发表基线复现出来（进度笔记里的 P1 仍欠着）。
- **算例规模仍偏小。** 40 算例覆盖了 4 规模 × 10 种子，但仍是 8–20 个客户，不足以做强的统计结论或逼近真实路网。
